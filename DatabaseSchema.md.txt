For KrishiPulse, we will use MongoDB Atlas as the primary database and Supabase Auth exclusively for user authentication.
Our database will store:
•	User profiles
•	ESP32 device information
•	Sensor readings
•	Pump commands
•	Irrigation history
•	Machine Learning predictions
I recommend creating 6 main MongoDB collections for the first version.
1. Database architecture
MongoDB Atlas
Database: krishipulse
users
User profiles
devices
ESP32 devices
sensor_readings
Sensor data
pump_commands
Pump commands
irrigation_history
Irrigation records
ml_predictions
ML predictions
Important: MongoDB does not require traditional SQL foreign keys. We will connect collections using ObjectId references and identifiers such as userId, deviceId, and commandId.
2. Collection 1 – users
Purpose: Store application user profiles.
Supabase Auth manages the actual login credentials. MongoDB stores the corresponding application profile.
Schema
Field	Data type	Description
_id	ObjectId	MongoDB document ID
authUserId	String	Supabase user ID
fullName	String	User's name
email	String	User's email
role	String	User role
createdAt	Date	Profile creation time
updatedAt	Date	Last profile update
Example document
{
  "_id": "ObjectId(...)",
  "authUserId": "supabase-user-123",
  "fullName": "KrishiPulse User",
  "email": "user@example.com",
  "role": "USER",
  "createdAt": "2026-11-21T10:00:00Z",
  "updatedAt": "2026-11-21T10:00:00Z"
}
Important rules:
•	authUserId must be unique.
•	Email should be synchronized from the verified Supabase identity.
•	Do not store passwords in MongoDB.
•	A user should only access their own authorized devices and data.
3. Collection 2 – devices
Purpose: Store information about registered ESP32 hardware devices.
Each physical ESP32 will have a unique device ID.
Schema
Field	Data type	Description
_id	ObjectId	MongoDB ID
deviceId	String	Unique hardware ID
userId	ObjectId	Owner's user document ID
deviceName	String	Device display name
deviceTokenHash	String	Hashed device credential
connectionStatus	String	ONLINE / OFFLINE
lastSeen	Date	Last device heartbeat
lastReadingAt	Date	Latest sensor reading time
pumpStatus	String	ON / OFF / UNKNOWN
operatingMode	String	MANUAL / AUTO
createdAt	Date	Registration time
updatedAt	Date	Last update
Example document
{
  "_id": "ObjectId(...)",
  "deviceId": "KP001",
  "userId": "ObjectId(...)",
  "deviceName": "Farm Sensor 01",
  "deviceTokenHash": "hashed-device-secret",
  "connectionStatus": "ONLINE",
  "lastSeen": "2026-11-21T10:00:00Z",
  "lastReadingAt": "2026-11-21T10:00:00Z",
  "pumpStatus": "OFF",
  "operatingMode": "AUTO",
  "createdAt": "2026-11-21T09:00:00Z",
  "updatedAt": "2026-11-21T10:00:00Z"
}
Important rules:
•	deviceId must be unique.
•	userId connects the device to its owner.
•	Store only a secure hash of the device credential, never the original secret.
•	Update lastSeen using a device heartbeat.
•	Do not assume a device is online simply because its last reading exists.
•	pumpStatus should reflect the last confirmed hardware state.
4. Collection 3 – sensor_readings
Most important IoT collection
Purpose: Store sensor data received from the ESP32.
Every valid sensor upload will create a new document.
Schema
Field	Data type	Description
_id	ObjectId	Reading ID
deviceId	String	ESP32 device ID
soilMoisture	Number	Calibrated soil moisture percentage
temperature	Number	Temperature in Celsius
humidity	Number	Relative humidity percentage
waterAvailable	Boolean	Water available or not
recordedAt	Date	Reading timestamp
receivedAt	Date	Backend reception timestamp
Example document
{
  "_id": "ObjectId(...)",
  "deviceId": "KP001",
  "soilMoisture": 35,
  "temperature": 30,
  "humidity": 60,
  "waterAvailable": true,
  "recordedAt": "2026-11-21T10:00:00Z",
  "receivedAt": "2026-11-21T10:00:01Z"
}
How it works
Suppose the ESP32 sends readings every 30 seconds.
Example sensor history
10:00:00
35% moisture
30°C
10:00:30
34% moisture
30°C
10:01:00
32% moisture
31°C
10:01:30
30% moisture
31°C
Illustrative readings. Each row is a separate MongoDB document.
We will use this collection for:
•	Live dashboard readings.
•	Historical moisture graphs.
•	Temperature and humidity charts.
•	ML model input.
•	Agricultural analytics.
Recommended: Use a compound index on deviceId and recordedAt so we can retrieve a particular device's recent readings efficiently.
5. Collection 4 – pump_commands
Purpose: Store every pump operation requested by the user or generated by automatic irrigation logic.
This collection acts as the command queue between the backend and ESP32.
Schema
Field	Data type	Description
_id	ObjectId	Command ID
deviceId	String	Target ESP32
userId	ObjectId	User who requested it, if applicable
command	String	PUMP_ON / PUMP_OFF
operatingMode	String	MANUAL / AUTO
commandStatus	String	Command lifecycle status
reason	String	Reason for the command
createdAt	Date	Command creation time
expiresAt	Date	Command expiry time
claimedAt	Date	Time device claimed command
acknowledgedAt	Date	Acknowledgement time
failureReason	String	Rejection or failure reason
Example document
{
  "_id": "ObjectId(...)",
  "deviceId": "KP001",
  "userId": "ObjectId(...)",
  "command": "PUMP_ON",
  "operatingMode": "MANUAL",
  "commandStatus": "PENDING",
  "reason": "Manual irrigation request",
  "createdAt": "2026-11-21T10:00:00Z",
  "expiresAt": "2026-11-21T10:02:00Z",
  "claimedAt": null,
  "acknowledgedAt": null,
  "failureReason": null
}
Command lifecycle
PENDING
Command created in MongoDB
CLAIMED
ESP32 retrieves command
EXECUTED
Operation completed
REJECTED
Safety check failed
EXPIRED and FAILED are additional possible terminal statuses.
Recommended statuses:
•	PENDING
•	CLAIMED
•	EXECUTED
•	FAILED
•	EXPIRED
•	REJECTED
Important: Commands should be claimed atomically, have an expiry, and be handled idempotently so polling or network retries cannot cause duplicate pump activation.
6. Collection 5 – irrigation_history
Purpose: Maintain a record of actual irrigation operations.
Whenever the pump starts successfully, the system can open an irrigation event. When the pump stops, the event is completed with its duration.
Schema
Field	Data type	Description
_id	ObjectId	Irrigation event ID
deviceId	String	ESP32 device
startCommandId	ObjectId	Pump ON command
stopCommandId	ObjectId	Pump OFF command, if applicable
operatingMode	String	MANUAL / AUTO
startTime	Date	Actual start time
endTime	Date / null	Actual end time
durationSeconds	Number / null	Actual pump runtime
status	String	RUNNING / COMPLETED / INTERRUPTED
stopReason	String / null	Why irrigation stopped
createdAt	Date	Record creation time
Example document
{
  "_id": "ObjectId(...)",
  "deviceId": "KP001",
  "startCommandId": "ObjectId(...)",
  "stopCommandId": "ObjectId(...)",
  "operatingMode": "AUTO",
  "startTime": "2026-11-21T10:00:00Z",
  "endTime": "2026-11-21T10:05:00Z",
  "durationSeconds": 300,
  "status": "COMPLETED",
  "stopReason": "Target moisture reached",
  "createdAt": "2026-11-21T10:00:00Z"
}
This collection will support:
•	Daily irrigation history.
•	Weekly irrigation reports.
•	Pump runtime calculations.
•	Water management analytics.
•	Historical automatic and manual irrigation records.
For the first prototype, we should track actual pump runtime. We should not claim exact water consumption unless we also calibrate and measure the pump's flow rate.
7. Collection 6 – ml_predictions
Purpose: Store Machine Learning predictions and irrigation recommendations.
Schema
Field	Data type	Description
_id	ObjectId	Prediction ID
deviceId	String	Related ESP32
sensorReadingId	ObjectId	Source reading
irrigationRequired	Boolean	Prediction result
recommendation	String	Suggested action
confidence	Number / null	Model confidence, if available
modelVersion	String	ML model version
createdAt	Date	Prediction timestamp
Example document
{
  "_id": "ObjectId(...)",
  "deviceId": "KP001",
  "sensorReadingId": "ObjectId(...)",
  "irrigationRequired": true,
  "recommendation": "Irrigation recommended",
  "confidence": 0.91,
  "modelVersion": "1.0",
  "createdAt": "2026-11-21T10:00:05Z"
}
The confidence value should only be stored when the selected model provides a meaningful and appropriately evaluated confidence or probability. It should not be invented.
8. Database relationships
Here is how the six collections connect with each other.
USERS
_id · authUserId · email · role
One user can own multiple devices
DEVICES
_id · deviceId · userId · status
One device can have many records
SENSOR_READINGS
Many readings
PUMP_COMMANDS
Many commands
IRRIGATION_HISTORY
Many irrigation events
ML_PREDICTIONS
Many predictions
In database terms:
Relationship	Type
User → Devices	One-to-many
Device → Sensor readings	One-to-many
Device → Pump commands	One-to-many
Device → Irrigation history	One-to-many
Device → ML predictions	One-to-many
Sensor reading → ML prediction	One-to-many or one-to-one, depending on prediction design
Pump command → Irrigation event	Referenced by command IDs
9. MongoDB indexes
Indexes are important because the database will continuously receive sensor readings.
I recommend these indexes:
Collection	Index	Purpose
users	authUserId unique	Find user profile
users	email	Search profile
devices	deviceId unique	Identify ESP32
devices	userId	List user's devices
sensor_readings	deviceId + recordedAt	Retrieve history
pump_commands	deviceId + commandStatus + createdAt	Find pending commands
irrigation_history	deviceId + startTime	Retrieve irrigation history
ml_predictions	deviceId + createdAt	Retrieve predictions
Example MongoDB index commands:
db.users.createIndex(
  { authUserId: 1 },
  { unique: true }
);

db.devices.createIndex(
  { deviceId: 1 },
  { unique: true }
);

db.devices.createIndex(
  { userId: 1 }
);

db.sensor_readings.createIndex(
  { deviceId: 1, recordedAt: -1 }
);

db.pump_commands.createIndex(
  { deviceId: 1, commandStatus: 1, createdAt: 1 }
);

db.irrigation_history.createIndex(
  { deviceId: 1, startTime: -1 }
);

db.ml_predictions.createIndex(
  { deviceId: 1, createdAt: -1 }
);
These are intended to be created once during database setup, not on every API request.

11. Recommended data validation rules
We should validate all incoming sensor data before saving it.
Field	Validation
soilMoisture	0–100
temperature	Valid configured sensor range
humidity	0–100
waterAvailable	Boolean
deviceId	Must belong to a registered device
command	PUMP_ON or PUMP_OFF
operatingMode	MANUAL or AUTO
recordedAt	Valid timestamp, with reasonable clock-skew checks
For soil moisture, we must calibrate the sensor before converting raw ADC readings into percentages. Temperature validation should account for the actual sensor's supported range.

13. My recommendation before implementation
We should follow this database creation order:
1.	Create MongoDB Atlas cluster.
2.	Create database named krishipulse.
3.	Create the six collections.
4.	Configure indexes.
5.	Set up the MongoDB connection in Node.js.
6.	Create Mongoose models.
7.	Connect the models with the API endpoints.
8.	Test the database using simulated sensor data.
One important architectural decision: Keep sensor readings as separate documents rather than embedding an ever-growing array inside the device document. This will make historical queries, analytics, and data management much easier as KrishiPulse grows.
The schema above is our proposed MVP database blueprint. We can extend it later for multiple farms, crop profiles, irrigation zones, and weather data without changing the core architecture.
