1.3 Authentication – Supabase Auth
Supabase SVG Icon - Free Supabase PNG & SVG Download
Technology: Supabase Auth
Authentication only – no application database
Supabase will handle user identity and login security.
It will provide:
•	User registration.
•	Email and password login.
•	Session management.
•	Access tokens.
•	Password recovery.
•	Logout.
How authentication works:
1.	User opens KrishiPulse.
2.	User enters email and password.
3.	React sends the credentials to Supabase Auth.
4.	Supabase verifies the credentials.
5.	Supabase returns an access token and session.
6.	React uses the access token when requesting protected backend APIs.
7.	Node.js verifies the token before providing access to protected operations.
Important: MongoDB will store application data. Supabase will manage the user authentication identity. We can store the Supabase user ID in MongoDB to associate a user with their devices and other records.

Scenario A: Monitoring soil moisture

4.	ESP32 connects to the internet using Wi-Fi.
5.	ESP32 sends the sensor data to the Node.js API.
6.	Node.js validates the data.
7.	MongoDB Atlas stores the sensor reading.
8.	React requests the latest dashboard data.
9.	The dashboard displays the updated moisture percentage.

Scenario B: Farmer turns ON the water pump
Analysis and experimental implementation of affordable smart irrigation system using IoT to reduce agricultural costs and minimize water usage | Applied Water Science | Springer Nature Link
link.springer.com
Suppose the farmer clicks the Pump ON button.
1.	React sends a request to the Node.js backend.
2.	Backend verifies the user's Supabase authentication token.
3.	Backend checks that the user is authorized to control the device.
4.	Backend stores a new pump command in MongoDB.
5.	ESP32 periodically checks the backend for pending commands.
6.	ESP32 receives the command.
7.	ESP32 checks safety conditions, such as water availability and maximum runtime.
8.	If safe, ESP32 activates the relay.
9.	The water pump starts.
10.	ESP32 sends an acknowledgement to the backend.
11.	Backend updates the command status.
12.	React dashboard displays the confirmed pump status.
Important: The pump should not turn ON merely because the website sends a command. The ESP32 must check local safety conditions before operating it.

8. Pump Control APIs
These APIs enable the farmer to operate the water pump through the dashboard.
Method	Endpoint	Purpose
POST	/api/pump	Create pump command
GET	/api/pump/status	Get confirmed pump status
GET	/api/command	ESP32 fetches pending command
POST	/api/pump-ack	ESP32 acknowledges command
8.1 POST /api/pump
React → Backend
Purpose: Request manual pump operation.
Example request:
{
  "deviceId": "KP001",
  "command": "PUMP_ON",
  "mode": "MANUAL"
}
Example response:
{
  "success": true,
  "message": "Pump command created",
  "command": {
    "commandId": "CMD001",
    "command": "PUMP_ON",
    "status": "PENDING"
  }
}
The response must not say that the pump is running yet. It only confirms that the request was accepted and saved.
8.2 GET /api/command
ESP32 → Backend
Purpose: ESP32 checks for pending commands.
Example:
GET /api/command?deviceId=KP001
Example response:
{
  "success": true,
  "command": {
    "commandId": "CMD001",
    "command": "PUMP_ON",
    "mode": "MANUAL",
    "expiresAt": "2026-11-21T10:02:00Z"
  }
}
If no command exists:
{
  "success": true,
  "command": null
}
The backend must atomically claim or lease a command so repeated polling does not cause the same command to be executed more than once.
8.3 POST /api/pump-ack
ESP32 → Backend
Purpose: Receive execution acknowledgement from the hardware.
Example request:
{
  "deviceId": "KP001",
  "commandId": "CMD001",
  "status": "EXECUTED",
  "pumpStatus": "ON"
}
Example response:
{
  "success": true,
  "message": "Command acknowledgement received"
}
Possible command statuses:
Status	Meaning
PENDING	Waiting for device
CLAIMED	Retrieved by device
EXECUTED	Operation completed
FAILED	Operation failed
EXPIRED	Command expired
REJECTED	Safety rules prevented execution
If the tank is empty, for example, the ESP32 must reject a pump ON command and send a REJECTED acknowledgement with a reason.
8.4 GET /api/pump/status
Returns the last confirmed physical pump state, not merely the last requested command.
Example:
{
  "success": true,
  "pumpStatus": "ON",
  "operatingMode": "MANUAL",
  "lastAcknowledgedAt": "2026-11-21T10:01:00Z"
}

12. Health Check API
GET /api/health
Purpose: Check whether the backend is running and whether its database connection is available.
Example response:
{
  "success": true,
  "service": "KrishiPulse API",
  "status": "HEALTHY",
  "database": "CONNECTED"
}
Do not expose credentials, internal infrastructure details, or sensitive diagnostic information in this endpoint.
13. API Authentication Structure
We have two types of API clients.
A. User authentication
1.	React obtains a Supabase access token.
2.	React sends the token in the Authorization header.
3.	Node.js verifies the token with Supabase.
4.	Node.js checks the user's permissions and device ownership.
5.	Authorized request proceeds to MongoDB.
B. Device authentication
1.	ESP32 stores its unique device credential.
2.	ESP32 sends the credential with each API request.
3.	Node.js verifies the credential against the registered device.
4.	Backend accepts or rejects the request.
Example user request header:
Authorization: Bearer SUPABASE_ACCESS_TOKEN
Example hardware request header:
Authorization: Bearer DEVICE_SECRET
These represent two separate authentication mechanisms. Never use a user's Supabase token as the ESP32 device credential.

15. API Response and Error Standards
Every API should use a consistent response structure.
Successful response:
{
  "success": true,
  "message": "Data retrieved successfully",
  "data": {}
}
Error response:
{
  "success": false,
  "message": "Unauthorized access",
  "error": {
    "code": "UNAUTHORIZED"
  }
}
Recommended HTTP status codes:
Code	Meaning
200	Successful request
201	Resource created
400	Invalid request
401	Authentication required
403	Permission denied
404	Resource not found
409	Conflict
422	Validation failed
429	Too many requests
500	Internal server error
503	Service unavailable
